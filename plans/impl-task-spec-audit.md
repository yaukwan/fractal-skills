## 建议

### F1：区分本次执行范围的检查与整份 spec 的完成检查

- 优先级：P2；置信度：高（文本缺少明确分支，实际错误发生率未验证）。
- 证据：`skills/impl-task-spec/SKILL.md:22` 限制执行范围；`:63` 允许子集完成后保持 `in_progress`；`:71` 无条件要求检查整份 spec 的成功标准与最终集成；`:73` 要求按整份 spec 推导状态。
- 触发场景：spec 包含独立任务 1.1 和 2.1，用户只授权 1.1。1.1 已通过验证，但整体验收依赖尚未实现的 2.1。
- 影响：执行者可能把未到执行阶段的整体验收当作失败检查，将正常的子集交付标为 `blocked`，或误将补齐整体验收视为扩展实现范围的理由。
- 建议：收尾先检查本次范围及其影响面；只有整份 spec 具备完成条件时，才执行用于宣告整份完成的验收。项目要求每次改动都运行的回归检查仍必须执行。尚未到期的整体验收记为待执行，不记为失败。
- 验收：仅授权 1.1 时，只完成 1.1，2.1 保持未完成，记录整体验收待执行，文档保持 `in_progress`。如果本次改动违反项目必需回归检查，则记录真实失败并按现有规则处理。
- 工作量：S；修改风险：中。需要避免把范围限制解释成跳过项目必需检查。

### F2：明确待交接与阻塞的状态优先级

- 优先级：P2；置信度：中（已有两类处理规则，但分界需要推断）。
- 证据：`skills/impl-task-spec/SKILL.md:64` 将无法推进的必需工作或最终检查定义为 `blocked`；`:72` 要求待阶段确认的交接保持 `in_progress`，同时又规定不可用的必需检查为 `blocked`。
- 触发场景：实施任务已完成，后续 review 必须由阶段负责人确认；当前没有进一步授权的实施任务可运行。
- 影响：同一项待确认工作可能被解释为正常等待，也可能被解释为必需检查不可用。不同执行者可能写入不同状态。
- 建议：明确正常阶段交接的等待条件与真实执行阻塞。例如，已明确责任方和下一步的待确认交接保持 `in_progress`；已到执行阶段但环境缺失、执行失败或无法交付的必需检查记为 `blocked`。把此规则归并到状态表，收尾步骤引用状态表。
- 验收：分别走查等待 review 确认、review 已开始但环境缺失、review 发现失败三种情况；每种情况都能唯一推导状态及下一步。最终状态仍以项目已有生命周期映射为准。
- 工作量：S；修改风险：低。不需要新增状态或修改上游模板。

### O1：为跨会话证据增加最小版本关联

- 类型：可选可靠性增强，不是已证实的缺陷。
- 证据：`skills/impl-task-spec/SKILL.md:23` 要求检查基线；`:24` 和 `:51` 要求判断证据是否失效；`:42` 的持久化字段包含命令、目录、结果和产物，但未要求记录这些结果对应的实现状态。
- 影响：仓库在会话间发生变化后，执行者需要重新调查旧结果与当前实现的关系；命令和结果相同不足以定位验证过的实现。
- 建议：每次执行记录一次基线 revision 与相关工作区改动说明；任务证据关联该执行记录。对未提交改动保留必要的差异或可复现产物引用。不要只记录 HEAD，因为验证对象可能包含工作区改动。无 Git 项目使用项目已有版本标识。
- 验收：验证后修改相关实现，再恢复执行，能够识别需重新验证的任务；只修改无关文档时，不应要求无差别重跑全部任务。
- 工作量：S；修改风险：低。保留按任务简洁回写，避免引入独立状态存储或原始日志。

### O2：明确承接已授权的逐任务原子提交

- 类型：与本次用户工作流相符的可选增强，不是现有授权规则的错误。
- 证据：`skills/impl-task-spec/SKILL.md:36` 已要求每个任务完成后立即回写；`:73` 正确规定任务完成本身不授权提交，但没有描述用户已要求逐任务提交时的顺序。
- 建议：在执行契约中识别用户或项目的提交策略。已授权逐任务提交时，顺序为任务验证、进度回写、检查任务差异、选择性暂存任务交付与进度、提交，再开始下一任务。保留原有“完成不等于授权提交”的边界。
- 失败处理：提交失败时保留已验证的任务状态，单独记录提交阻塞；逐任务提交是用户要求的检查点时，解决前不进入下一任务。已有无关暂存内容不得被夹带提交。
- 验收：已授权时，每个提交包含该任务交付与对应进度；无授权时不提交；预先暂存的无关变更保持原状；提交失败不把已通过的行为验证改写成失败。
- 工作量：S；修改风险：中。主要风险是误提交其他协作者的暂存内容。仅 HEAD 不能证明一次验证对应提交后的完整树状态。
